Changes since v1.6: new S group (scene adherence, S1–S8) and H group (held out, H1–H3); choosing which cases run;
feedback trigger in Role-play. C1–C6 and D1–D2 are unchanged.

===== HOW TESTS RUN (applies to every case) =====
- Each case is a NEW chat (new Dify conversation); turns in one case share the chat.
- Each turn names its mode. The runner sends the message exactly as the app would: "[QA] " or "[RP] " + the message.
- Quotation marks enclosing a test message only delimit it; quotes inside a message are sent as normal characters.
- Button and card taps are written as the exact text the app sends when they're tapped.
- Feedback in Role-play is triggered the way the app's hint describes: the learner sends "feedback".
- The hidden <character …/> line comes only with the first reply of a custom scene, so later turns in the same scene
  never check for it. A turn that starts a new custom scene (e.g. S5 T2) does.

Profile (same as the live app)
- Each case has a Start profile (empty unless given). Before every turn the runner sends the current profile as
  learner_profile, formatted the same way the live app formats it.
- After every turn, any hidden <profile …/> line is read and merged into the current profile the same way the live app
  saves it, so later turns get exactly what the live app would send. Cases never type a later-turn profile by hand.

Two kinds of checks
- AUTO (required): decided by the runner. Any failed AUTO check = the attempt FAILS.
- REVIEW (advisory): behavior only a person can judge. The runner prints the reply beside it. REVIEW items never
  block a green result; they're listed under "For review" so you can skim them when you have time.

Results
- Each case runs once. A FAIL is rerun once: fails twice = FAIL; passes on rerun = FLAKY (reported, not a failure).
- Green run = every case PASS or FLAKY. The report shows PASS / FAIL / FLAKY counts, then every case (passed or
  failed) with each turn's message, its checks (✓ / ✗), REVIEW items, and the full reply, hidden lines included.

Choosing which cases run
- Default run: every case except held-out ones (C, D and S groups).
- Pick cases by ID ("C1 D2") or by group letter ("S" = S1–S8). In GitHub: Actions → Golden set → Run workflow,
  "Case IDs to run". Locally: EVAL_CASES="S".
- Held-out cases (H group) run only when named ("H" or "H1 H2 H3") or with EVAL_HELD_OUT=1.
- App and repeats (GitHub): production, staging or both; 1–3 runs per app. Apps alternate within each round. With more
  than one run, the report opens with a table of first-try passes per case and app (e.g. "S3: 2/3 (1 flaky)").
  Running the same prompt on both apps measures run-to-run variation; after a prompt change, it's the before/after.

Text the AUTO checks look at
- "Visible text" = the reply with hidden self-closing tags (<name attr="…"/>) removed. Text checks are not case-sensitive.
- "Raw reply" = the reply as Dify returned it. Hidden-line checks use the raw reply.

AUTO check types
- starts with "…" / contains "…" / contains any of […] / doesn't contain any of […]   (visible text)
- link: lesson link | no link   (lesson link = a bilibili.com or b23.tv URL from the course)
- profile: <field> contains any of […] / <field> = "…" / fields present: […] / no profile line
- character line: present | absent
- bracket line: present   (at least one [ … ] line in the reply, e.g. a scene setup or cue)
- feedback score ≥ N   (parses "Course score: X/5")
- no feedback   (no "Course score")
- words ≤ N   (visible text)
- list items ≥ N   (lines starting with •, -, * or a number)
- example sentence: present   (at least one quoted sentence of 4+ words, "…" or “…”)
- sandwich steps < 2   (fewer than 2 of these step groups appear: [partially agree | partial agreement | partly agree],
  [keep the discussion open | keep it open], [move forward together]). One mention is fine; listing the method's
  steps as the answer is not.

Shared phrase lists (S and H groups)
- MENU = ["Reply with a number", "Disagree with a coworker"]   (signs of the fixed scene menu)
- INTRO = ["Start with your introduction", "introduce yourself"]   (meeting-opener prompts)
- ICE FEEDBACK = ["introductions, context", "introduce yourself", "start with your introduction", "self-introduction"]
  (feedback graded on the meeting-opening method: Introductions, Context, Expectations). Specific phrases, not the
  single word "introduction", so feedback like "good introduction of the problem" doesn't fail.

Global checks (every reply, every case; AUTO)
- G1 Every video link is a real course lesson link (no invented links).
- G2 No mention of Taiwan (visible text and hidden lines).
- G3 When the learner's message has no Chinese, the visible reply has at most 5 Chinese characters.
- G4 Hidden lines, when present, are well formed (<profile learner_…="…"/>, <character name="…" gender="…"/>).

Fixed lines: C1, C2, C6 and D2 expect the tutor's fixed lines "outside what I can help with" (out-of-scope reply)
and "This is covered in the course:" (opening of an answer the course covers).

===== SCENE ADHERENCE TESTING =====
Custom scenes stay custom: no fixed scene menu, no meeting-opener prompts, and feedback that fits the scene.
Two failures seen in the Dify logs (Oct 16–29): choosing the wrong experience (fixed menu or opener instead of the
requested scene) and using the wrong grading criteria (an on-topic scene graded on the meeting-opening method).
Covered elsewhere: "Start a meeting" on request → C3, C4; custom scene with profile → C5; mode switch → D1.
